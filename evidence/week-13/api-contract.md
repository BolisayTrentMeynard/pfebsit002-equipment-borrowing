# API Contract (Week 13)

Written from the code in `backend/routes/api.php`, the controllers and the middleware. Base URL in the demo: `http://127.0.0.1:8000/api`. All bodies are JSON. All data is fake test data.

## Common rules

- **Authentication:** every endpoint except `POST /login` needs `Authorization: Bearer <token>`. Tokens are stored hashed on the server and expire after 8 hours.
- **Roles:** `borrower`, `approver`, `staff`. The role is read from the stored user, never from the request.
- **Correlation id:** every response has an `X-Correlation-ID` header (generated by the server). The same id appears in log lines and audit entries.
- **Errors are always JSON**, never an HTML page.

| Status | Meaning | Body |
|--------|---------|------|
| 401 | Missing, invalid or expired token, or wrong login | `{"message": "Unauthenticated."}` or `{"message": "Invalid credentials."}` |
| 403 | Role not allowed, or a borrower viewing someone else's request | `{"message": "This action is not allowed for your role."}` |
| 404 | Record does not exist | `{"message": "..."}` |
| 409 | Invalid state change (for example approving a request that is already released) | `{"message": "Cannot approve a request that is RELEASED."}` |
| 422 | Validation failed, nothing saved | `{"message": "...", "errors": {"field": ["..."]}}` |
| 429 | Too many login attempts (limit 10 per minute) | `{"message": "Too Many Attempts."}` |

## Endpoints

| Method and path | Who | Request | Success | Errors |
|-----------------|-----|---------|---------|--------|
| `POST /login` | anyone | `email` (required, email, max 255), `password` (required, max 255) | 200 `{token, expires_in_hours, user:{id,name,role}}` | 401, 422, 429 |
| `GET /me` | any logged in | none | 200 `{id, name, role}` | 401 |
| `POST /logout` | any logged in | none | 200 `{message}` (token deleted) | 401 |
| `GET /equipment` | any logged in | none | 200 `{data:[{id,name,asset_tag,status}]}` | 401 |
| `GET /requests` | any logged in (borrower sees only own) | optional `status` = PENDING, APPROVED, REJECTED, RELEASED, RETURNED or CLOSED | 200 `{data:[request]}` | 401, 422 |
| `GET /requests/{id}` | any logged in (borrower: own only) | none | 200 `{data: request + audit logs}` | 401, 403, 404 |
| `POST /requests` | borrower | `equipment_id` (required, exists), `reason` (required, 3 to 255), `requested_days` (required, 1 to 7) | 201 `{data: request}` status PENDING | 401, 403, 422 (equipment not available, or already an open request for it) |
| `POST /requests/{id}/approve` | approver | optional `note` (max 255) | 200 `{data}` status APPROVED | 401, 403, 404, 409 |
| `POST /requests/{id}/reject` | approver | optional `note` (max 255) | 200 `{data}` status REJECTED | 401, 403, 404, 409 |
| `POST /requests/{id}/release` | staff | none | 200 `{data}` status RELEASED, due date stored | 401, 403, 404, 409 (also if the equipment is not available) |
| `POST /requests/{id}/return` | staff | `inspection_result` (required: good, damaged, missing_parts), optional `inspection_notes` (max 255) | 200 `{data}` status CLOSED | 401, 403, 404, 409, 422 |
| `GET /custody` | approver, staff | optional `overdue=1` | 200 `{data:[{request_id, equipment, borrower, due_at, overdue}]}` | 401, 403, 422 |
| `GET /manual-handling` | approver | none | 200 `{data:[notification]}` (only FAILED_NEEDS_HUMAN) | 401, 403 |
| `POST /manual-handling/{id}/resolve` | approver | `note` (required, 3 to 255) | 200 `{data}` status HANDLED_MANUALLY | 401, 403, 404, 409 (not in FAILED_NEEDS_HUMAN), 422 |
| `GET /up` | anyone | none | 200 (Laravel health check) | none |

## Request status flow

```
PENDING -> APPROVED -> RELEASED -> RETURNED -> CLOSED
   \-> REJECTED
```

Any other jump returns 409 and leaves the status unchanged. Every change writes an audit entry (who, from, to, correlation id).

## Reminder notification status flow

```
PENDING -> SENT
PENDING -> SENT_AFTER_RETRY
PENDING -> FAILED_NEEDS_HUMAN -> HANDLED_MANUALLY
```

Notifications are created by `php artisan reminders:run`, not by an API call. The API only lists the failed ones and lets an approver mark them handled.

## Not in the API (known limits)

- No password reset, registration or token refresh. Users come from the seeder; log in again after expiry.
- The real notifier is a stand-in (writes a log line), so no email or SMS is sent.
