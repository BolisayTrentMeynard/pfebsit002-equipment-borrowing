# Acceptance Criteria (Week 16)

Numbering continues from Week 15 (AC-25 to AC-38). Expected results and thresholds are written before any run. Actual results go in the test matrix in the evidence round. Values marked "proposed" may be refined in a later chunk before the work they govern is built; any change is written in the lab log with the date.

| ID | Category | Given / When | Expected result | Checked by |
|----|----------|--------------|-----------------|------------|
| AC-39 | Workload models | Before any measurement | Two workload models (ordinary and peak) are written with users, think time, journey mix, duration, data size and thresholds, plus the assumptions behind them and their limits | `workload-models.md`, commit order |
| AC-40 | Baseline | One user, one request at a time, 30 repeats per endpoint, on staging | p50, p95 and p99 recorded for `/up`, readiness, login, equipment, requests, custody, detail and the writes; errors 0; login is timed separately | k6 summary |
| AC-41 | Ordinary load | Ordinary model: 5 users, 5 min steady | Reads p95 under 800 ms, writes p95 under 1500 ms, errors under 1%; throughput and CPU and memory of php, mysqld and caddy recorded | k6 summary, sampling CSV |
| AC-42 | Peak, spike and endurance | Peak model, spike, and (if run) the short endurance run | Peak: p95 under 2000 ms and errors under 2%. Spike: the observed p95, error rate and recovery time are recorded whether or not a threshold is met. After every counted run the data integrity check finds no corruption. A missed threshold is reported as a finding with its cause, not hidden. The 20 min run, if done, is labelled as not a real endurance test | k6 summary, SQL checks |
| AC-43 | Health endpoints | The system is up, and then the database is stopped | `/up` (Laravel built-in, liveness) answers 200 without using the database. `GET /api/health/ready` answers 200 with body ok when the database and queue table are reachable, and 503 with body fail when not. Neither body holds a host, version, path or error text | PHPUnit, manual during chunk 4 |
| AC-44 | Structured log | Any API call on staging | One `http.request` log line with route, status, milliseconds and correlation id. The line holds no email, name, token, password, request body or query string. A log search for those finds nothing. A call to an unknown API path is logged too, with route `unmatched` and no correlation id (the correlation id middleware only runs for matched routes) | PHPUnit, log search |
| AC-45 | Monitoring and incident detection | A monitoring map and a walkthrough of one incident | The map lists each signal (liveness, readiness, request log, failed jobs, manual-handling backlog, log size, latency), where it is read, a threshold, and a named owner (the developer, with a stated response time for the course context). The walkthrough shows how the MySQL outage is detected from those signals alone | `monitoring-map.md`, chunk 4 capture |
| AC-46 | Environment separation | Dev, staging and a production target on paper | A comparison table lists database name, `APP_ENV`, `APP_DEBUG`, `LOG_LEVEL`, HTTPS certificate, secrets location, web server, queue and scheduler handling for each. Staging uses its own database `equipment_staging`, `APP_DEBUG=false`, and its example file holds no secrets. The production column says plainly what is not built | `environment-comparison.md`, `.env.staging.example` |
| AC-47 | Repeatable release | Release script run on a clean staging database | One documented command sequence builds the Flutter release, migrates and seeds `equipment_staging`, starts the API and Caddy, and runs the health checks. The Week 15 Postman collection (149 tests) and `php artisan test` (61 tests, plus the new ones) pass on the result. Narrow-width and desktop screenshots of the new-request form are taken on the staged build | Developer run, Postman, PHPUnit, screenshots |
| AC-48 | Failure test | MySQL stopped during the ordinary workload, prediction committed first | The observed behavior is compared with the prediction. Liveness stays 200, readiness turns 503, API errors are generic 500s without internals, no partial write exists, and the system recovers without restarting php or Caddy. Any difference is recorded | k6, health polling, log search |
| AC-49 | Notifier timeout (closes AC-34) | The receiver does not answer within the 5 s timeout | The notifier treats it as a transient failure; after 3 attempts the item is FAILED_NEEDS_HUMAN. Tested without waiting 5 s in real time by faking the HTTP call | PHPUnit with `Http::fake` |
| AC-50 | Bottleneck fixes | Measurements confirm at least 2 bottlenecks | For each fix kept: test written first, before and after numbers from the same workload and data, cause named, and the Flutter app and Week 15 collection unchanged. A candidate the measurements do not confirm is not fixed and is recorded as such. If fewer than 2 are confirmed, the evidence says so instead of inventing a fix | PHPUnit, k6 before and after |
| AC-51 | Backup and rollback | `mysqldump` of staging, restore, then back to the `week-15` tag | The dump restores into a scratch database with the same table list and row counts. After going back to `week-15` the API answers `/up`, the Week 15 collection passes, and the Week 16 readiness route is absent (404). The steps and time taken are written down | Developer run, captures |
| AC-52 | Readiness recommendation | End of the week | A conditional recommendation, never the words "production ready". It lists conditions that must hold, limitations of the measurements, risks still open, and a one-page tabletop review of an incomplete release package (Activity 2) | `readiness-recommendation.md` |
| AC-53 | Secrets | The Week 14 and 15 secret scans are repeated after Week 16 | No signing key, `APP_KEY` value, `.env`, token or password in `laravel.log`, `equipment_staging` dump files, the repo or the evidence zip. The new `http.request` log line and the k6 scripts are included in the scan. Dev-only seed passwords are named and excluded | Developer scan |

## Thresholds in one place (decision D5, proposed)
| Run | Reads p95 | Writes p95 | Errors |
|-----|-----------|------------|--------|
| Ordinary | under 800 ms | under 1500 ms | under 1% |
| Peak | under 2000 ms (all requests) | under 2000 ms | under 2% |
| Spike | recorded, no pass/fail threshold | recorded | recorded |

The thresholds are targets for this prototype on this PC. They are not an agreement with real users. A missed target is a result.
